RLS en Supabase para apps de Lovable: cómo saber si tu base está abierta y cerrarla paso a paso

Respuesta corta: en una app de Lovable con Supabase, la clave pública que va en el navegador (anon o, en proyectos nuevos, sb_publishable_) es pública por diseño. Lo único que impide que cualquiera lea o modifique tus tablas es Row Level Security (RLS). Revisá que cada tabla del esquema public tenga RLS activado, una política por operación filtrada por auth.uid() y ninguna política using (true) sobre datos privados.

Por qué importa: los datos

  • Sentris escaneó 2.144 repositorios públicos de Supabase hechos con herramientas de IA (agosto de 2026): el 40,6% tenía una exposición crítica confirmada, contra el 24,9% de un grupo de control sin IA. En los repos de Lovable la cifra fue 57,9% (fuente).
  • En 2025, Matt Palmer encontró 170 de 1.645 apps de Lovable con datos expuestos por falta de RLS, el caso registrado como CVE-2025-48757 (fuente).
  • UpGuard explica la causa: Supabase activa RLS por defecto en las tablas creadas desde el Table Editor, pero no en las que se crean por API o SQL, que es como trabajan los agentes de código (fuente).

La documentación oficial de Supabase lo dice sin vueltas: una tabla de un esquema expuesto sin RLS se puede leer y escribir con cualquier rol que tenga permisos sobre ella (fuente).

Paso 1: mirá el escaneo de seguridad de Lovable

Lovable corre un Quick scan cada vez que abrís el diálogo de publicar. Entre otras cosas, marca tablas sin RLS y políticas que dejan pasar a todos. También podés lanzarlo cuando quieras desde la vista Security del proyecto, y las políticas se revisan en More → Database → Manage → Policies (documentación de Lovable). Es un buen primer filtro, pero la propia Lovable aclara que no garantiza seguridad completa.

Paso 2: listá las tablas sin RLS con SQL

En Supabase, abrí el SQL Editor y ejecutá:

select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
order by rowsecurity, tablename;

Cada fila con rowsecurity = false es una tabla abierta. Después mirá qué políticas tenés y para quién:

select tablename, policyname, cmd, roles, qual, with_check
from pg_policies
where schemaname = 'public';

Buscá políticas con qual = true dirigidas a anon o public: equivalen a no tener RLS, salvo que esa tabla sea realmente pública.

Paso 3: probá desde afuera, como lo haría un atacante

Solo en tu propio proyecto: con la URL y la clave anon que ya están en el frontend de tu app, pedí una fila de una tabla privada.

curl "https://TU-PROYECTO.supabase.co/rest/v1/perfiles?select=*&limit=1" \
  -H "apikey: TU_CLAVE_ANON"

Si devuelve datos sin haber iniciado sesión, esa tabla está expuesta. Una respuesta vacía ([]) o un error de permisos es lo que querés ver.

Paso 4: activá RLS y ajustá los permisos

Supabase recomienda tres cosas juntas: activar RLS, quitar los permisos por defecto a anon y authenticated, y devolver solo los que tu app usa.

alter table public.perfiles enable row level security;
revoke all on table public.perfiles from anon, authenticated;
grant select, insert, update, delete on table public.perfiles to authenticated;

Con RLS activado y sin políticas, nadie lee nada con la clave pública. Ahora agregá una política por operación:

create policy "ver mi perfil" on public.perfiles
  for select to authenticated
  using ( (select auth.uid()) = user_id );

create policy "crear mi perfil" on public.perfiles
  for insert to authenticated
  with check ( (select auth.uid()) = user_id );

create policy "editar mi perfil" on public.perfiles
  for update to authenticated
  using ( (select auth.uid()) = user_id )
  with check ( (select auth.uid()) = user_id );

create policy "borrar mi perfil" on public.perfiles
  for delete to authenticated
  using ( (select auth.uid()) = user_id );

El with check del update evita que alguien se “regale” una fila cambiando el user_id. Agregá un índice en user_id para que las consultas no se vuelvan lentas.

Paso 5: los cinco errores que vemos más seguido

  1. using (true) en datos privados. Deja pasar a cualquiera. Usalo solo para contenido público, como un catálogo.
  2. Vistas que saltan RLS. En Postgres las vistas se crean como security definer y devuelven todo. Crealas con with (security_invoker = true).
  3. Funciones security definer en el esquema public. Se pueden llamar desde la API con los privilegios de su dueño. Ponelas en un esquema privado y fijá search_path = ''.
  4. Políticas basadas en user_metadata. El usuario puede modificar ese campo. Para roles y permisos usá app_metadata.
  5. La clave service_role o sb_secret_ en el frontend. Salta todo RLS. Si alguna vez estuvo en tu repo, rotala en Supabase.

Paso 6: comprobalo con tests

Supabase propone un archivo de test por tabla en supabase/tests/ (pgTAP) que verifique qué puede y qué no puede hacer cada rol, y correrlo con supabase test db. Hasta que el test pasa, no sabés si la política hace lo que creés.

Si preferís pedírselo a Lovable

Podés escribir en el chat del proyecto algo como: “Activá Row Level Security en todas las tablas de public, quitá los permisos de anon que no hagan falta y creá políticas separadas de select, insert, update y delete filtradas por auth.uid() = user_id. No uses using (true) en tablas con datos de usuarios.” Después volvé a correr el escaneo y repetí la prueba del paso 3.

Preguntas frecuentes

¿Cómo sé si mi app de Lovable tiene la base de datos abierta?

Ejecutá en el SQL Editor de Supabase: select tablename, rowsecurity from pg_tables where schemaname = 'public'. Toda tabla con rowsecurity = false está abierta para cualquiera que tenga la clave anon, que es pública. También podés probar con curl usando la clave anon contra una tabla privada.

¿Supabase activa RLS automáticamente?

En las tablas creadas desde el Table Editor, sí. En las creadas por SQL o por API, que es como trabajan los agentes de IA, no: hay que ejecutar alter table ... enable row level security en cada una.

¿Alcanza con activar RLS?

No. Con RLS activado y sin políticas nadie accede; después necesitás una política por operación filtrada por auth.uid(), quitar los permisos de anon que no uses y evitar using (true) en datos privados.
